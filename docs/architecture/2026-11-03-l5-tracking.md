# L5 — Minimal tracking (design note)

Status: APPROVED FOR AUTONOMOUS MODE

Every user-visible behaviour is set by the approved brief (§5.1 Chart.js vendored, §6 L5 with the indicators table and the RM rules, §7 storage model incl. `rm_measured` and `app_setting`, §8 history and progress routes, §10 dependencies), the L5 "Done when" of `docs/roadmap.md`, invariants 7 to 12 and D-021, D-022, D-033, D-041, D-053, D-062, D-064, D-066. This note fixes what they leave open and records it as D-067 to D-071; none is superseded (D-061's "any action on a closed session redirects" is narrowed for set and setting corrections exactly as D-066 announced: "L5 in history"). **No schema change**: every L5 fact fits 0001 (`rm_measured` has `n`, `weight_g`, `measured_on`, `created_at`, `deleted_at`; `app_setting` holds the formula); 0001 to 0004 stay frozen, and a revision `0005` is added only if the performance test (section 9) proves an index is needed. One vendored asset (Chart.js, named by brief §5.1 and §10), no Python dependency. No `/build-roadmap` stop condition applies: no decision superseded, no released data format changed, no data can be lost (every delete is soft), and each choice either follows the brief or is a detail it leaves to the architect (pagination, chart axis, rounding, flag rule wording, navigation).

## Context

Milestone L5: session history (list, detail, online correction of a set or setting, soft delete of a session); per exercise: last performance, records, chart of the main indicator over time from a JSON route; indicators by category; RM measured / estimated with a global formula; sessions per week. Done when: changing the formula recomputes estimates without touching measured RMs; a measured RM wins on display and an estimate above an older test is flagged; warm-ups and sets above 12 reps are excluded from estimation; a corrected set changes the indicators, a deleted session disappears from history and indicators but stays in the database; charts render in < 1 s with one year of simulated history.

Current state (end of L4, head `0004`): `domain/indicators` (`RECORD_TYPES`, `LoggedSet`, `is_record`, `records`, `Volume`, `volume`, `round_count`) is the single place for records and volume. `storage/sessions` filters every per-exercise read with `_live_session` (`session.deleted_at IS NULL`) and live sets: `last_performance(…, except_session_id)`, `last_settings`, `record_history` (counted sets by `(completed_at, id)` with `session_id`), `recent_exercise_ids`, `latest_session`. `services/sessions.update_set` / `delete_set` take `require_open` (L5 passes `False`, D-066); `save_settings` requires an open session; a closed `GET /seances/{id}` renders `session_summary.html` (per-exercise counted sets, volume, ⭐ count). `storage/app_settings.get` / `put` exist (docstring announces the RM formula). `rm_measured` has no query, service or route. `_nav.html` has three links; `static/vendor/manifest.json` + `tests/unit/test_web_assets.py` check vendored hashes; `request-errors.js` is the only first-party script; `docs/ui-spec.md` "Platform" already allows JavaScript "for charts".

## Chosen design

### 0. Schema

None. Deleting a session sets `session.deleted_at` (0001 column, already honoured by `uq_session_one_open` and every reader). `rm_measured` rows are created by the RM form and soft-deleted (`deleted_at`). The formula is `app_setting` key `rm.formula`. If section 9 shows a missing index (candidate: `session (user_id, started_at)` for the history page), it is added as an additive revision `0005` (`op.create_index`, no rebuild, declared in `schema.py`) in the storage commit, tested from empty and from `0004`; none is added speculatively.

### 2. History (D-067)

- **List** `GET /historique`: non-deleted sessions of the user, newest first by `(started_at, id)`, **20 per page by keyset** (`?avant={session_id}`; « Plus anciennes » loads the next page with `hx-get`, appended, and works as a plain link). Items are grouped under **month headings** (`month_key(local_date)`, a heading repeated at the top of a page only when the month continues). Each item is one link to `/seances/{id}`: local date and start time, template name or « Séance libre », location, exercises with at least one live set, counted sets, load volume (`indicators.volume`, kg; omitted when zero). An open session shows the tag « En cours ». Sessions with no live set are listed (they exist; the user can delete them) with « Aucune série ». Records are not computed on the list (they need each exercise's full history); the detail shows them.
- **Consistency** at the top of the history page (section 6).
- **Detail** = `GET /seances/{id}` of a closed session (one URL per session, the L4 summary extended): the summary totals as today, then per exercise with live sets: settings (editable), every live set in order (warm-ups included, type tag, ⭐ recomputed), each with « Modifier » (`<details>` with the same field macros as L4, `PATCH /series/{id}`) and « Supprimer » (`DELETE /series/{id}`, soft, no confirmation as in L4), a link « Progression » to the exercise; at the bottom « Supprimer la séance ». An open session keeps its L4 page (edit and delete already there) and gains the same « Supprimer la séance » at the bottom.
- **Correction** reuses L4's paths and services (D-066): `services.sessions.update_set` / `delete_set` with `require_open=False`, and `save_settings` gains the same flag. Validation is `domain/sessions.set_draft` / `setting_draft` against the exercise's **current** fields (values of variables archived or unlinked since are kept by `replace_set_values`, invariant 8). No set can be added to a closed session (not in the brief), no change of date, location or exercise. Answer: the corrected exercise's section of the detail page (`session_detail_exercise.html`), totals out of band, announcement « Série 2 modifiée. ». Every reader recomputes from facts, so the corrected set changes records, stars, e1RM, charts, last performance and prefill at once (roadmap criterion).
- **Delete a session** `DELETE /seances/{id}` after an in-place confirmation (L2 component, safe answer focused, `GET /seances/{id}/suppression`, `?annuler=1`): `session.deleted_at = now` (sets, rows and settings untouched: one fact, the session's flag). Allowed open or closed. Answer `HX-Redirect: /historique`. Effect: every reader already filters `session.deleted_at IS NULL` (`_live_session`): the session leaves history, records, stars, volumes, e1RM, charts, consistency, last performance, prefill, last settings, recent exercises and the home preselection; an open deleted session frees `uq_session_one_open`. The rows stay in the database (roadmap criterion, tested with a direct query). No restore in V1 (not in the brief); L6's export includes deleted sessions with their `deleted_at`.

### 3. Per exercise: progress page (D-068)

`GET /progression/{exercise_id}` (any exercise of the user, archived included; 404 otherwise). Sections, in order:

1. **Header**: name, category, link to the exercise sheet.
2. **Dernière performance**: `storage.last_performance(user_id, exercise_id, except_session_id=None)`, the D-062 definition (live sets of the most recent non-deleted session holding one, open session included), date and sets as `Display.set_text`.
3. **Chart of the main indicator** (section 7) with its data table in a closed `<details>` « Voir les données » (accessible alternative and no-script fallback): one row per point with the secondary indicators of that session.
4. **Records** (`indicators.bests`, counted sets of live sessions, each with its date and a link to the session):

| Category | Main indicator (chart, one point per local date) | Records and secondary shown |
|---|---|---|
| `strength` | best e1RM of the day's estimable work sets (formula of the setting); second series « 1RM mesuré » (points) | RM table (section 5); max load per rep count (1 to 12, and « 13+ »); best session volume Σ reps × load |
| `kettlebell` | max reps in one set **at each load**: one series per load (the 6 most used loads) | max reps per load; density Σ reps / Σ duration over sets holding both (reps / min), shown only when durations are logged; best session volume |
| `bodyweight` | max reps in one set; for an exercise without a reps field, max duration (holds) | max reps, max duration, max added load (sets with `weight_g`), best session reps total |
| `cardio` | Σ distance of the day when the exercise has a distance field and the day has one, else Σ duration | max distance, max duration, best pace (« 5:20 /km ») and speed (« 11,3 km/h ») over sets holding both |
| `intervals` | number of counted rounds of the day (D-041) | max rounds in a session, max Σ work duration in a session |

Warm-ups never count (D-064). A day with two sessions is one point (max for "max" indicators, sum for "Σ" ones). The source of each quantity is `set_entry` core columns only; variables never enter indicators (D-064).

`GET /progression` (index, nav « Progression »): exercises with at least one live set in a live session (`exercises_with_history`), most recent first: name, category, last date, number of sessions; each links to its page. Empty state links to the home page.

### 4. Indicators, pure (D-068, D-069)

- Input: `LoggedSet`s from `record_history` (one indexed query per exercise, already counted types only, now with `local_date`) plus `rm_test_sets` / `measured_of` for the RM table. Nothing is stored (invariant 9, D-021); no cache.
- `main_series` returns `Series(key, label_key, unit_kind, points: [Point(local_date, value)])` with canonical integers; the web layer turns them into display numbers through `units.chart_number` and labels through `fr.json`.
- `sessions_per_week(local_dates, today, weeks=12)`: ISO weeks starting Monday, oldest first, ending with the week of `today`; each date counted once per session.

### 5. RM (D-069)

- **Formulas** (`w` load, `r` reps, result in grams): Epley `w·(1 + r/30)` (default), Brzycki `w·36/(37 − r)`, Lombardi `w·r^0.10`, O'Conner `w·(1 + r/40)`, Wathan `100·w/(48.8 + 53.8·e^(−0.075·r))`. A single (`r = 1`) is its own 1RM for every formula (no formula inflates a real single). The result is rounded to the nearest 100 g (`ESTIMATE_STEP_G`), the precision shown, so comparisons and display agree. `load_for_reps(formula, one_rm, n)` is the exact inverse, also rounded to 100 g.
- **Estimable set**: type `work`, `1 ≤ reps ≤ 12`, `weight_g > 0`. Warm-ups, RM tests (they are measurements) and sets above 12 reps are excluded (roadmap criterion). The estimate is the **best e1RM over the exercise's history** (live sessions), with the date and the set it comes from.
- **Measured RM**, one write per fact (D-033): manual entries (`rm_measured`, live) and `rm_test` sets with `reps = n` and `weight_g > 0` (read directly). For each `n`, the **latest** measurement (by date, then the heavier on the same day) is the measured nRM: a test describes the current level, the records section keeps the all-time max per rep count.
- **RM table** (`rm_table`), strength only: one row for `n = 1` always, plus one row per `n` with a measurement. Each row: the measured value (origin « mesuré », date, « saisie » or « test en séance »), else the estimate (origin « estimé (Epley) »: `load_for_reps(best 1RM, n)`). **A measured value wins on display**; the estimate is shown beside it, secondary. **Flag**: when the estimate exceeds the measured value and its source set is **later** than the measurement, the row carries « Estimation supérieure au test du {date} » (an older test, overtaken). An estimate above a *newer* test is not flagged (the test wins and is the newer fact).
- **Formula setting**: `app_setting` `rm.formula` (absent or unknown → Epley, `formula_of`). Changing it changes only the estimates on the next render: measured rows are facts and are never rewritten (roadmap criterion).
- **Manual entry** `GET /rm/{exercise_id}` (navigation → 303 to `/progression/{id}#rm`; htmx → the RM section) and `POST /rm/{exercise_id}` `{n, weight, date}`: `n` 1–12 (« 1 » preselected; chips 1, 3, 5 and an input), weight typed in kg through `domain/units` (`weight` kind), date `<input type="date">` (ISO, native picker, no script) defaulting to today's local date, not in the future. Stored `measured_on` (local date), `created_at = now`. Answer: the RM section re-rendered with « 1RM mesuré enregistré. »; refusal `200` with messages (D-050). Each manual entry in the « Mesures » list has « Supprimer » (`DELETE /rm/mesures/{id}`, soft, `deleted_at`). No edit (delete then re-enter). `rm_test` sets are corrected in their session like any set. Non-strength exercise → 404-like refusal `rm_not_strength` (the section is never offered).

### 6. Consistency: sessions per week (D-070)

Counted: non-deleted sessions (open or closed) holding at least one live set, by their `local_date`. Shown at the top of `/historique`: the last 12 ISO weeks as a server-rendered list of bars (one row per week: « sem. du 27/10 », count, a bar whose width comes from a class `bar--0` … `bar--7` (7 = « 7 et plus »), no inline style) and the 12-week average (« 2,8 séances / semaine »). The current week is marked « en cours ». No chart script on that page.

### 7. Chart: Chart.js, JSON route, script (D-068)

- **Vendored** `static/vendor/chart.umd.min.js`: Chart.js 4.x (MIT), pinned version, source URL and SHA-256 in `manifest.json`; the existing manifest test covers it. Loaded only on `progress.html` (`{% block scripts %}` added to `base.html`, `defer`), with `static/js/progress-chart.js`. No date adapter: the x axis is a **category axis** of local dates (labels « 03/11 », from the server), which needs no second vendored file.
- **JSON** `GET /api/progression/{exercise_id}`: `{"unit": "kg", "axis": "<label>", "labels": ["03/11", …], "series": [{"label": "1RM estimé (Epley)", "kind": "line" | "points", "values": [102.5, null, …]}]}`: values already in display units (`units.chart_number`), labels and unit text from `fr.json`, aligned on one label list (`null` where a series has no point). Behind the device middleware; `/api/` GETs get the `Origin` / `Sec-Fetch-Site` check and `no-store` (D-047). Empty history → `{"labels": [], "series": []}`.
- **Script** `progress-chart.js` (the third first-party script role the ui-spec already allows; no French, no rule, no unit conversion): for each `canvas[data-chart-src]`, `fetch` the URL (same origin, credentials default), build one Chart with `animation: false`, `responsive: true`, `maintainAspectRatio` from the CSS box, colours read from CSS custom properties (`getComputedStyle`, tokens of `tokens.css`, re-read on `prefers-color-scheme` change), the axis title and series labels from the JSON. On success it sets `data-chart-state="ready"` and `data-chart-ms` (time from navigation start, `performance.now()`); on failure `data-chart-state="error"` and reveals the server-rendered `[data-chart-error]` text (from `fr.json`), the data table staying available. `canvas` carries `role="img"` and an `aria-label` describing the main indicator; the table is the accessible alternative.
- **CSP intact**: no inline script or style, no `style=` attribute in templates; Chart.js sets canvas size through the CSSOM (`element.style.*`), which `style-src 'self'` does not block; the browser test asserts no CSP violation (`securitypolicyviolation` listener) in Chromium and WebKit. If a pinned version injects a `<style>` element, the developer picks the nearest 4.x that does not, or stops and reports (no CSP change without a decision).

### 8. Settings page and navigation (D-070)

- `GET /reglages` → `settings.html`: one section « Estimation du 1RM »: five radio chips (L4 `.chips`), each with the formula name and its formula text (« Epley : charge × (1 + rép. / 30) »), the current one checked; `PATCH /reglages` `{rm_formula}` on `change` (L4 settings pattern, no save button), answer the section with the saved state (`kind="ok"`) and « Formule enregistrée : Brzycki. ». Unknown value → `200` refusal `invalid_choice`.
- **Navigation**: `_nav.html` gains « Historique » (`section = "history"`) and « Progression » (`section = "progress"`), before the catalog links (history is the frequent need after logging). « Réglages » is **not** in the main nav (one setting, rarely changed, and the nav already needs two rows at 360 px): it is linked from the RM section of every strength exercise (« Formule : Epley · Changer ») and from the progression index header. The ui-designer lays out five links at 360 px within the L3 rules (no horizontal scroll, 48 px targets, deterministic rows).
- Entry points to a progress page: the progression index, the exercise sheet (« Progression »), each exercise of a session detail.

### 9. Performance (D-071)

- Reads per progress page: exercise, fields, `record_history` (one query, index of 0004), `last_performance`, `rm_test_sets` and `measured_of` (strength), the formula; the JSON route reads `record_history` and the RM facts again. Everything is in-memory Python over at most a few thousand sets.
- **Test** `tests/integration/test_progress_performance.py` reuses the L4 one-year history builder, moved from `test_session_performance.py` to a shared helper `tests/support/history.py` (the L4 test imports it, no behaviour change): about 5 000 sets, with RM tests and manual RMs added. Through the TestClient (paired, middlewares on), 10 timed rounds of `GET /progression/{id}` + `GET /api/progression/{id}` for the busiest strength exercise and the cardio one: **median of the pair < 1 s** (expected tens of ms), same rationale as D-066's refinement (median only, runs in the default `-n auto` run). Also `GET /historique` (first and a middle page) median < 1 s.
- **Browser** (`tests/e2e/`): the same history built in the live server's database; open the progress page in Chromium and WebKit, wait for `data-chart-state="ready"`, assert `data-chart-ms < 1000`, no CSP violation, no external request.
- Remedy order if slow: query shape, then an index in `0005` (section 0); never a cache (D-021).

### 11. Error handling

| Failure | User sees | Left in the database |
|---|---|---|
| Invalid correction of a set or setting | `200` section re-rendered, values kept, message per input (D-050) | nothing |
| Correction of a set of a deleted session, or a deleted set | 404 → « Non enregistré, réessayer » (D-053) | nothing |
| Delete of an already deleted or foreign session | 404 | nothing |
| Invalid RM entry (n outside 1–12, weight unparsable or zero, bad or future date) | `200` RM form with messages | nothing |

## Rejected options

- **A separate history detail page (`/historique/{id}`) beside the closed session summary**: two pages for one closed session; the summary extended with corrections is the detail.
- **Adding sets to a closed session or reopening it**: not in the brief (D-061 "no reopen in V1"); correction is of existing sets and settings.
- **Page numbers / offset pagination**: keyset on `(started_at, id)` is stable when a session is deleted between pages.
- **A records count on each history item**: needs every exercise's full history per page; the detail shows stars.
- **Storing e1RM or a "measured" copy of rm_test sets in `rm_measured`**: invariant 9 and D-033.
- **Estimating from RM-test sets**: they are measurements; reading them as both would count one fact twice.
- **Best measured nRM = all-time max**: a test describes the current level; the all-time max is already the « max load per rep count » record.
- **Raw formula output in grams**: « 103,333 kg » is noise; 100 g matches the display and makes the flag comparison stable.
- **Formula applied to singles**: Epley turns a real 100 kg single into 103,3 kg.
- **Chart data in `data-` attributes of the page**: the brief names a JSON route, and a year of points in an attribute bloats the page; the route also serves a future client (D-039).
- **Chart.js time scale with a date adapter**: a second vendored file for even spacing; category labels suffice for a personal trend.
- **Server-rendered SVG charts (no Chart.js)**: the brief names Chart.js; an SVG renderer would be custom drawing code to maintain.
- **Unit conversion or formatting in the chart script**: business and display rules stay on the server (D-015, invariant 2).
- **A chart for sessions per week**: a list with CSS bars carries 12 numbers without a script on the history page.
- **« Réglages » in the main nav**: a sixth link for one rarely changed setting at 360 px.
- **A revision 0005 index added up front**: only when measured (D-066 practice).
- **Restoring a deleted session**: not in the brief; the data stays for export (L6).

## UI design

Status: APPROVED FOR AUTONOMOUS MODE. Every choice applies the brief (§4, §6 L5), D-053, D-061 to D-070 and the L1a–L4 ui-spec, or is a presentation detail left to the ui-designer (D-070 asks it to lay out the five-link header). The full screen specification, every French string and its key are in `docs/ui-spec.md` "L5 — …" (one copy); this section gives the reasons and the deltas the developer must know.

### Task and decision

- **Historique** (`/historique`): task « find a session to check or correct it, and see whether I train regularly ». Decision: which session to open. Information: date and weekday, template name, place, size (sets, volume), exercises; the weekly count against the 3–5 target.
- **Session detail** (closed `/seances/{id}`): task « fix a set or a setting logged wrong, or remove a session that should not exist ». Decision: which set to change, or delete the session. Information: every live set with type and ⭐, the settings, the totals.
- **Progression** index: task « open the exercise I want to review ». Information: name, category, last date, number of sessions, most recent first.
- **Progression of an exercise**: task « am I progressing, and what is my max now ». Decision (strength): which load to use or whether to retest. Information, in order of use: last performance, the 1RM (measured or estimated, with its origin and the flag), the main indicator over time, the records.
- **Réglages**: task « choose the 1RM formula ». Decision: one of five. Information: each formula's name and expression, which one is current.

### Header: five links, three rows on the phone

Measured at 16 px weight 600: brand ≈ 150, « Historique » ≈ 80, « Progression » ≈ 95, « Exercices » ≈ 80, « Variables » ≈ 75, « Séances types » ≈ 115 px, for 328 px of width at 360. No pair of nav links fits beside the brand (150 + 80 + 95 + 2 × 16 = 357), and the five links need 445 px plus gaps: three rows are unavoidable without shortening labels or hiding links.

- **Choice: two link groups, each on its own row below 40rem.** Row 1 the brand; row 2 « Historique  Progression » (tracking: used after every session, also on the phone); row 3 « Exercices  Variables  Séances types » (management, mostly desktop; unchanged L3 order and width, 302 px). Ordered by frequency of use, grouped by task, deterministic: the header looks the same on every page and never jumps. Markup: one `<nav>` holding two `<ul class="site-nav__list">` (the first `site-nav__list--tracking`); below 40rem `.site-nav` is a column; each list keeps `flex-wrap: wrap` as the last fallback for a very wide system font.
- Cost: the phone header grows from 97 to 145 px (three 48 px rows + divider), at the top of the page only, not sticky. Nothing is fixed at the bottom: the bottom of the screen stays free for the session ✓. The session page is reached at `#seance-plan` (L4), so its first ✓ does not move. The resume state of home uses `.main--nav`, whose `min-height` becomes `calc(100dvh - 3 * var(--target-min) - 1px)` so « Reprendre la séance » stays at the bottom of the screen.
- From 40rem: brand left, the two groups right on one row (group gap `--space-6`, link gap `--target-gap`, links padded `--space-2`): ≈ 150 + 565 = 715 px, one row from ≈ 760 px; between 640 and 760 px the existing header wrap puts the nav on a second row (brand, then both groups).
- Rejected: a menu button (one more tap on every navigation, rejected in L3), a bottom tab bar (takes the thumb zone of the session page and needs a fixed element over content), « Réglages » as a sixth link (D-070), shortened labels (« Hist. », « Prog. » are unreadable), « Historique » alone beside the brand (still three rows, mixes groups).

### Main layout choices

- **History**: month sections (`h2` « Novembre 2026 ») of L2 `.rows`, one link per session, newest first; above them a compact **12-column week chart** (server-rendered `<ol>`, CSS bar heights) instead of the note's 12 horizontal rows: 12 rows take ≈ 290 px at 360 before the first session; columns take ≈ 110 px and read as a trend at a glance. Every column carries its count as visible text; the week date is visible from 40rem and always in the accessible text. Average and « Cette semaine » are written as text.
- **Session detail**: the L4 summary keeps its head and totals; each exercise section gains the L4 settings `<details>` and the L4 set rows with « Modifier » (same markup, same ids, same component), and a « Voir la progression » link; the session delete sits last, separated from « Retour à l’accueil » by a section gap, behind the in-place confirmation.
- **Progress page**: one column on the phone in the order of use (last performance, RM, chart, records). From 64rem two columns `minmax(0, 1fr) minmax(0, 2fr)`: left (DOM first) last performance and RM, right the chart and the records; visual order = DOM order = keyboard order.
- **RM**: one row per n (not a table: four columns do not fit 328 px): « 1RM » and the shown value (`--text-lg`, tabular) on one line, then muted lines for the origin, the estimate beside a measured value, and the flag. Manual entry in a `<details>` « Saisir un RM mesuré »: **twelve chips 1–12** in a fixed 6-column grid (6 × 48 + 5 × 8 = 328 px: exactly two rows at 360) instead of « chips 1, 3, 5 and an input »: one tap, no keyboard, the L4 chip component; weight input (kg), native date input.
- **Settings**: the five formulas as L2 `.choice` radio rows (name weight 600, expression muted under it), not chips: each option carries a two-part label that does not fit a chip.

### Chart

- Box `<div class="chart" hidden>` holding the `canvas[data-chart-src]`; the script removes `hidden` when it starts, so with JavaScript off nothing empty is shown and the caption and table remain. Height `15rem` below 64rem (328 × 240 px at 360), `20rem` from 64rem (≈ 770 × 320 px in the right column at 1280); `maintainAspectRatio: false`, width 100 % of the column. `.chart` sets `font-size: var(--text-sm)`; the script reads its computed font size and family for Chart.js.
- **Accessible alternative, three layers**: (1) a visible `<figcaption>` written by the server (span of days, latest and best value), (2) the canvas `role="img"` `aria-labelledby` the section `h2` and that caption, (3) the data table in a closed `<details>` « Voir les données », newest first, `--text-sm`, columns chosen per category to fit 328 px (ui-spec). Charts are not drawn under two days of data: the caption says why and the table holds the one day.
- **Legend in HTML, not in the canvas**: a server-rendered `<ul class="chart-legend">` (only when there are ≥ 2 series), each item a coloured shape glyph (CSS `::before`, alt text empty) and the series label; Chart.js `plugins.legend.display: false`. The canvas legend's toggle clicks are neither keyboard-reachable nor 48 px.
- **Colours from tokens, never colour alone**: series *i* uses `--chart-{i}` and Chart.js `pointStyle` *i* (circle, rectRot, rect, triangle, crossRot, star; legend glyphs ● ◆ ■ ▲ ✕ ★ in the same order); axis ticks and titles `--color-muted`, grid `--color-divider`, tooltip `--color-surface` background, `--color-text` text, `--color-border` border. Lines 2 px, points radius 4 (measured 1RM: points only, radius 5). `spanGaps: true` (kettlebell loads are not logged every day). `interaction: {mode: "index", intersect: false}` so a tap anywhere on a day shows its tooltip. Tokens re-read on a `prefers-color-scheme` change, then `chart.update()`.
- **French formatting without French in the script**: Chart.js `locale` = `document.documentElement.lang` (« fr »: comma decimals in ticks and tooltips through `Intl`); the tooltip line comes from the JSON field `tooltip` (`progress.chart_tooltip`, « {label} : {value} kg », unit filled by the server, `{label}` / `{value}` substituted by the script). JSON delta: `"tooltip"` added beside `unit` and `axis`.
