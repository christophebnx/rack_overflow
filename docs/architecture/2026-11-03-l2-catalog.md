# L2 — Catalog: exercises and variables (design note)

Status: APPROVED FOR AUTONOMOUS MODE

Every user-visible behaviour is set by the approved brief (sections 4, 6 L2, 6.1, 7, 8), the L2 "Done when" of `docs/roadmap.md`, invariants 7 to 12 and D-018, D-020, D-021, D-030 to D-032, D-034, D-036, D-046, D-050. This note fixes what they leave open and records it as new, non-superseding decisions D-053 to D-057 (D-053 refines D-050, as D-050 itself announced). No schema migration is needed (head stays `0002`; 0001 / 0002 untouched), no released data format changes, no dependency is added.

## Context

Milestone L2: variable catalog (shared, created in the UI, D-030), exercises, `exercise_field` (D-031), aliases with normalised fuzzy search, the exercise seed of brief §6.1, plus the open points left by L1a / L1b: the general htmx error display (« Non enregistré, réessayer », focus return, clearing old messages), the first navigation items and brand / content alignment, `movement_pattern` free text vs vocabulary.

Current state (end of L1b): schema at `0002` already holds `variable`, `exercise`, `exercise_field`, `exercise_alias`, `app_setting` with every column L2 needs (checked below); no catalog query, service, route or page exists; `web/` has home, pairing and error pages, `components.css` has `.field`, `.input`, `.field__error`, `.field__hint`, buttons and `.actions--thumb`; `base.html` has an empty `nav` block and the `#annonce` live region; htmx 2.0.11 + json-enc 2.0.3 are vendored; `rack migrate` upgrades and nothing else.

## Chosen design

### 0. Schema check (no migration)

| Need | Where it lives today |
|---|---|
| variable code, label, type, unit, scope, enum values `{key, label}`, decimal scale, archive | `variable` (checks for type, scope, enum ⇔ values, decimal ⇔ scale 1–6) |
| exercise name, category, movement pattern, equipment, location, archive | `exercise` (`uq(user_id, name)`, checks) |
| core quantity **or** variable, required, increment, default, discrete values, order | `exercise_field` (`one_source`, `increment > 0`, `one_default`, `discrete_values` JSON, `position`, uniques per exercise) |
| aliases normalised | `exercise_alias` (`alias`, `alias_normalised`, `uq(exercise_id, alias_normalised)`, index) |
| seed marker | `app_setting(user_id, key, value)` |

Normalised exercise names are **not** stored: search normalises names in memory (section 4), so no column is added. Case- and accent-insensitive name uniqueness is checked by the service (single user, `BEGIN IMMEDIATE` serialises writes); the exact `uq(user_id, name)` stays the database backstop.

### 1. Variables (D-030, D-032, D-054)

- **Create**: label (1–40 chars, stripped), type (`VARIABLE_TYPES`), scope (`set` « mesure » / `setting` « réglage »), unit (free text ≤ 12 chars, **only** for `int` and `decimal`; for `weight` / `distance` / `duration` the unit follows the type, D-055; `enum` / `bool` / `text` have none), decimal scale (1–3 in the UI, within the 1–6 of the CHECK; required iff `decimal`), enum values (required iff `enum`, 1–50 labels of 1–40 chars, unique after `normalise`).
- **Code**: never typed by the user. `variable_code(label, taken)` = `slug(label)`, suffixed `_2`, `_3`… on collision with any code of the user (archived included); fixed at creation, never changed (the label may change). Empty slug (label of symbols only) → `v`, then suffixes.
- **Enum keys**: `enum_values(labels, existing)` keeps the key of every existing value (matched by position in the edit form, which carries the key in a hidden field), and gives new values `slug(label)` (suffix on collision; empty → `e`). A key is never reused or changed; only labels and order change (D-032). Removing a value whose key appears in `used_enum_keys` → problem `enum_value_in_use`; unused values may be removed. Example: « Siège », enum, labels « 1 » … « 10 » → keys `1` … `10`.
- **Edit** (`PATCH /variables/{id}`) changes the one row, so it applies to every linked exercise by construction (no copy per exercise). Label, unit, enum labels and order, added enum values: always editable. Type, scope, decimal scale: editable only while `has_values` is false (problem `frozen_after_use`), since stored integers and value tables depend on them. When type changes on a variable already linked, field parameters incompatible with the new type (increment, default, discrete values) are cleared on its links in the same transaction.
- **Archive / restore**: `archived_at` set / cleared; always allowed. An archived variable is not offered when adding a field; its existing links stay listed on the exercise page marked archived; L4 does not show archived variables in logging. History keeps its values.
- **Delete**: offered only when `has_values` is false: removes the variable's `exercise_field` links and the row, one transaction, after an in-place confirmation. With values: refused (`variable_in_use`; the UI shows « Archiver » instead and no delete button; the database FK without `ON DELETE` also refuses). This is the roadmap's "a variable linked to exercises with history cannot be deleted" (invariant 8).
- **Value storage column** (`value_column`, used by L4): `int`, `decimal`, `duration`, `distance`, `weight`, `bool` (0 / 1) → `value_int`; `enum` (key), `text` → `value_text`.

### 2. Exercises, fields and aliases (D-031, D-054)

- **Exercise**: name (1–80 chars; unique per user after `normalise`, archived included → `name_taken`), category (`EXERCISE_CATEGORIES`), movement pattern (optional free text ≤ 40), equipment (optional free text ≤ 40), location (`gym` / `home` / `both`). Archive / restore only (no delete, invariant 8): archiving sets `archived_at` and touches nothing else; archived exercises leave the list and search unless « afficher les archivés » is on.
- **Movement pattern stays free text** (D-054): L3 menus are named by the user (« Ischios / fessiers », « Bras », « Gainage ») and a menu lists its exercises explicitly (`template_slot_option`), so nothing needs a closed list; a vocabulary would need a migration per new pattern. Consistency comes from suggestions: the form's `<datalist>` offers the user's existing patterns (and equipments), and the service stores the first-seen spelling when a typed value equals an existing one after `normalise` (« tirage horizontal » → « Tirage horizontal »).
- **Default fields on create** (`default_fields(category)`): `strength`, `kettlebell` → reps (required, +1) and weight (required, +2.5 kg); `bodyweight` → reps (required, +1); `cardio` → duration (required, +30 s) and distance (optional, +100 m); `intervals` → duration (required, +30 s; one set = one round, D-041). The user edits them afterwards; this saves the common taps.
- **Field rules** (`field_params`): `required` bool; `increment` positive canonical integer, only for numeric kinds (core quantities, `int`, `decimal`, `weight`, `distance`, `duration`), null for `enum` / `bool` / `text`; `discrete_values` 1–30 distinct positive canonical integers, stored ascending, numeric kinds only, and exclusive with `increment` (problem `increment_with_discrete`: the stepper uses one or the other); `default` parsed with the field's kind into `default_int`, or `default_text` for `enum` (must be an existing key) and `text`, and must be one of the discrete values when they exist. Values are typed in display units and parsed by `domain/units` (D-055).
- **At least one measure**: an exercise always keeps at least one core quantity or `set`-scope variable (`check_measures`; removing the last → `last_measure`). A variable is linked at most once per exercise, a core quantity too (existing uniques).
- **Order**: new fields go last; `move_field(up | down)` swaps positions and renumbers `0..n-1` in one transaction. Buttons, no drag (accessible, works on touch).
- **Remove a field**: deletes the `exercise_field` row only; stored `set_entry` columns and `set_value` / `exercise_setting` rows stay (brief §7.1).
- **Aliases**: 1–60 chars; `alias_normalised = normalise(alias)`; refused when empty after normalisation, equal to the exercise's normalised name, or already an alias of the same exercise (`alias_taken`). The same alias on two exercises is allowed (search returns both). Remove deletes the row (an alias is configuration, not history).

### 3. Units (D-055, `domain/units.py`)

Storage stays canonical (invariant 7). Display and input, French conventions (decimal comma, ui-spec):

| Kind | Display | Input accepted |
|---|---|---|
| `int` (reps…) | `12` | digits |
| `weight` | kg, up to 3 decimals, trailing zeros dropped: `16`, `2,5`, `1,25` + `unit.kg` | number in kg, `,` or `.`; more than 3 decimals refused |
| `distance` | below 1000 m: metres `400` + `unit.m`; else km up to 3 decimals `5,2` + `unit.km` | bare number = km; suffix `m` or `km` accepted (`400 m`, `5,2 km`) |
| `duration` | `m:ss` under 1 h, `h:mm:ss` from 1 h | `m:ss`, `h:mm:ss`, or a bare number of seconds |
| `decimal` | value / 10^scale with exactly `scale` decimals, comma | number with ≤ scale decimals |
| `bool` | `field.yes` / `field.no` keys | checkbox |
| `enum` | the value's label | select by key |

Negative numbers, non-numbers and overflow (> 10^9) → `UnitError` with a stable code (`not_a_number`, `too_many_decimals`, `negative`, `too_large`, `bad_duration`) mapped to `catalog.error.*`. L4 reuses the same functions for steppers and set display.

### 4. Normalisation and fuzzy search (D-056, `domain/search.py`)

No new dependency: the catalog is about a hundred names and aliases, so ranking in Python over one query's rows takes well under a millisecond, and a library (rapidfuzz) would add a compiled wheel to the NAS install for no measurable gain.

`rank(query, candidates)`: `q = normalise(query)`; empty → every candidate, by `normalise(name)` (L4 passes `recent` ids to put them first). Each candidate text (its name and each alias, normalised) is scored; the candidate keeps its best score; score 0 is dropped; order by score desc, then position in `recent`, then normalised name; `limit` 20.

| Score | Rule (first that matches, per text) |
|---|---|
| 100 | text == q |
| 90 | text starts with q |
| 80 | every token of q is a prefix of a distinct token of text (any order): « dev couch » |
| 70 | q has no space, ≥ 2 chars, and is a prefix of the initials of the text's tokens, ignoring the stop-words `a, au, aux, d, de, des, du, en, et, l, la, le, les, un, une`: « dc » → « Développé couché (barre) » (`d c b`) |
| 60 | q is a substring of text |
| 40 | every token of q of ≥ 4 chars is within edit distance 1 (≥ 8 chars: 2) of the same-length prefix of a token of text, shorter tokens prefix-match: « devlope » → « developpe » |

Edit distance: a bounded Levenshtein in `domain/search.py` (short tokens, early exit beyond the bound). The roadmap examples: « DC » (alias `DC` → 100, also initials → 70), « bench » (alias `Bench press` → 90), « developpe » (name → 90) all find « Développé couché (barre) ». `GET /exercices/recherche?q=` calls `services.exercises.search`, which loads `search_candidates` and calls `rank`.

### 5. Seed (D-057)

- **Data**: `storage/seed_data/exercises.json`, a list of `{name, category, movement_pattern, equipment, location, fields: [{quantity, required, increment | discrete_values}], aliases: [...]}` with canonical integers. Core quantities only (D-030). Validated through the same `domain/catalog` validators as the UI (one rule set); a unit test checks it validates and holds exactly the 41 names of brief §6.1.
- **When**: `rack migrate` runs `seed_catalog` after the upgrade, in its own transaction, for `SINGLE_USER_ID`. No `rack seed` command (one way to do it); `rack update` seeds through `rack migrate`, so the user's NAS database gets the catalog on the L2 update.
- **Idempotence**: `app_setting` key `seed.version` (text integer). The seed has numbered steps: step 1 = exercises (L2); L3 adds step 2 = templates. Steps above the stored version run, then the version is stored, all in one transaction; a second `rack migrate` does nothing. Within a step, an exercise whose normalised name already exists for the user is skipped (a user who created « Planche » by hand keeps his). A user who renames or archives a seeded exercise never gets it back.
- **Tests and done-when**: the shared `migrated_engine` fixture does **not** seed (`upgrade_to_head` only), so the roadmap scenario "create « Kettlebell swing » … create « Vélo »" runs on an empty catalog; separate tests cover the seeded content (the seeded « Kettlebell swing » has the 16 / 20 / 24 kg discrete loads, « Vélo » duration + distance).

### 7. htmx error display (D-053, the L1a / L1b open point)

D-050 stays for refused input. For everything htmx does not swap — 4xx / 5xx answers, network failure, timeout — one first-party script `web/static/js/request-errors.js` (CSP `script-src 'self'`, loaded `defer` after htmx in `base.html`, no French text, no business logic):

- Listens to `htmx:afterRequest` on `document.body`; acts when `detail.successful` is false and the response has no `HX-Redirect` header (a revoked device follows the redirect to `/appairage`, D-049). htmx has already re-enabled the `hx-disabled-elt` elements at that point, and has not swapped, so the form keeps its values.
- Target: `detail.elt.closest("form")`, else `detail.elt`'s nearest `[data-request-scope]` container, else nothing but the live region.
- In the target: clears previous refusal state (removes `aria-invalid`, hides every `.field__error` with `hidden` and removes its id from `aria-describedby`), fills the target's `[data-request-status]` slot (`<p class="form-status" data-request-status hidden>`, rendered by the `_form_status.html` macro in every htmx form, the pairing form included) with `document.body.dataset.notSaved` (the server renders `data-not-saved="{{ t('error.not_saved') }}"` on `<body>`), un-hides it, writes the same text in `#annonce`, and moves focus to the form's first enabled `input` / `select` / `textarea`, else to the trigger element.
- On `htmx:beforeRequest` from the same target, the slot is hidden and emptied, so a retry starts clean.
- `htmx-config` gains `"timeout": 10000` so a stalled request on a weak gym network ends in this message instead of a button stuck disabled.
- Server side: unchanged (`{"error": code}` JSON for htmx). The message is the same for every failure (« Non enregistré, réessayer »): the user's action is the same, retry.

A test asserts that every `hx-post` / `hx-patch` / `hx-delete` element in the templates is or sits inside an element with a `[data-request-status]` slot.

### 9. Error handling summary

| Failure | User sees | Left in the database |
|---|---|---|
| Invalid input (label, number, duplicate name, enum value in use, last measure, frozen type…) | `200` form re-rendered, message per field, announced (D-050) | nothing (transaction not started or rolled back) |
| Race on a unique (normalised check passed, `uq` fails) | same as duplicate name (`NameTakenError` → `name_taken`) | nothing |
| Delete of a variable with values | `variable_in_use` message; the page offers archive | nothing |
| Unknown / foreign id | 404 page or `{"error": "not_found"}` → « Non enregistré, réessayer » | nothing |
| 5xx, network failure, timeout | form kept, « Non enregistré, réessayer » under it, focus on its first field (D-053) | nothing or the whole transaction |
| Seed data unreadable or invalid | `rack migrate` exits 1 (`StorageError` / `DomainError`) after the schema upgrade committed; rerun after the fix | schema upgraded, no seed row (seed transaction rolled back) |

## Rejected options

- **Alembic data migration for the seed**: a frozen migration can never be corrected, cannot skip names the user already created by hand, and puts French data in a migration; the versioned seed step in `rack migrate` is idempotent and testable.
- **`rack seed` as a separate command**: one more step to forget in the NAS guide; `rack migrate` already runs on every install and update.
- **Seeding on server start-up**: a write outside the operator's command and on every restart path; migrate is the one place the database changes shape and content.
- **Stored `name_normalised` column on `exercise`**: a migration and a second copy to keep in sync, for a catalog ranked in memory in under a millisecond.
- **SQLite FTS5 / trigram**: SQLite-only (D-016 asks for Postgres-compatible SQL) and no accent folding without a custom tokenizer.
- **rapidfuzz** (or any fuzzy library): a compiled dependency for ~100 strings; not named in brief §10.
- **`difflib` ratio as the only score**: ranks « DC » and prefix typing badly; explicit tiers are predictable and testable.
- **Movement pattern as a vocabulary**: menus need free names (« Bras », « Ischios / fessiers »); a closed list needs a migration per pattern.
- **Variable code typed by the user**: a technical identifier with no meaning to the user; derived from the label once.
- **Enum keys = labels**: renaming would break history (D-032).
- **Physical delete of a variable with values** or of exercises: forbidden by invariant 8; archive instead.
- **htmx `responseHandling` with HTML error fragments for 4xx / 5xx**: covers server answers only, not network failures or timeouts (the gym case), and changes the swap rules of every route; one client-side handler covers all failures.
- **`hx-on` inline handlers**: need `allowEval` and inline script (CSP, D-047).
- **Native `hx-confirm` (`window.confirm`)**: not stylable, focus and wording not under our control; the in-place confirmation fragment (« Annuler » focused, « Supprimer » secondary-danger) needs no script.
- **Field parameters on the variable** (one increment for all exercises): a dumbbell and a machine need different steps; D-031 puts them on the link.
